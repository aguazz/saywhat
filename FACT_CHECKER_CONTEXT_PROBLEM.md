# Debate Analyzer — Data Quality & Context Loss Problems

> **Status: Implemented (2026-06-02).** All five prompts below have been applied.
> See `truth_checker/entity_glossary.py`, `transcript_cleaner.py`, and the updated
> `verifier.py`, `extractor.py`, `segmenter.py`, and `app.py` for the implementation.



Two related problems sit upstream of the analysis pipeline. Both stem from the same root: the pipeline runs on raw ASR output without pre-processing, and individual stages receive only their immediate inputs with no broader debate context.

---

## Problem 1 — Fact-Checker Context Loss

### What `verifier.py` receives per claim

```python
user_msg = (
    f"Claim: {claim['text']}\n"
    f"Speaker: {claim.get('speaker', '')}\n"
    f"{_warrant_line}"
    f"\n{evidence_section}"   # web search results only
)
```

**That is all.** No transcript. No surrounding turns. No other claims. No entity glossary.

### Where context is stripped

```
Transcript (utterances)
  → segmenter.py     one turn at a time    →  turns
  → extractor.py     one turn at a time    →  claims (verbatim text)
  → classifier.py    one claim at a time   →  type / checkable / query
  → threader.py      all claims (IDs only) →  threads
  → deduplicator.py
  → [Run Fact-Check]
  → evidence.py      one claim query       →  web results
  → verifier.py      claim text + results  →  verdict    ← CONTEXT LOST
```

### Concrete failing example

**Claim `claim_6_0`** (turn_index 6, 00:33–00:48):
```
"Los trabajos de Kiss han sido severamente contrastados por décadas de investigación
con ensayos clínicos estándar de oro y le han dado la razón."
```

**Verifier output:**
> 'Kiss' is a common surname… the most likely candidate is **Jenő Kiss** or researchers associated with unorthodox treatments.

**Wrong.** "Kiss" = **Ancel Keys**, American nutritionist. Spanish-speaking debaters pronounced "Keys" as "Kiss"; the ASR transcribed it accordingly.

**Evidence available in the transcript that the verifier never sees:**

| Turn | Speaker | Fragment |
|------|---------|----------|
| 7 | B | `"Los estudios de Ansel Kiss están financiados por la NIH"` |
| 35 | B | `"Los estudios de Ancel Keys están financiados por la NIH"` |
| 52 | A | `"Ancel Keys fue el primero que aplicó análisis de regresión multivariable"` |

The full identity appears one turn later and is repeated a dozen times throughout the debate.

### Why this is structural, not a prompt problem

The verifier prompt is correct and the model behaved honestly. The fault is in the pipeline design: entity identity is stripped during extraction and never re-attached downstream.

### Affected claim categories

- **Phonetic variants of proper names** ("Kiss" for "Keys")
- **Nicknames / short forms** used consistently within the debate
- **Pronouns or demonstratives** ("él", "su estudio", "esto que comentó")
- **Partial references** ("the study", "his research")

Cross-turn entity references (entity introduced with a nickname in turn N, full name only in turn N+1) are assessed as **edge cases** in the current corpus — the more common failure is in-turn ambiguity. This affects which fix to prioritize (see Recommendations).

## Problem 2 — Raw ASR Output Enters the Pipeline Without Cleaning

### 2a — Entity name variants

The ASR transcribes what it hears. When speakers consistently mispronounce a proper name, every downstream stage operates on the wrong token. This is fundamentally an **entity normalization problem**: multiple surface forms in the same transcript refer to the same entity and need to be unified before analysis begins.

Examples from the "Debate Alimentario" transcript:
- `"Kiss"` / `"Ansel Kiss"` / `"Ancel Keys"` → same person
- `"el estudio de los 7 países"` → Seven Countries Study

The verifier sees whichever variant ended up in each claim. The `suggested_query` field generated by the classifier is also based on the claim's text, so fragmented variants produce fragmented web searches.

**Scope:** Current evidence is insufficient to determine whether this problem extends beyond proper names to technical terms or common vocabulary. The solution should be designed for proper names first but kept general enough to handle other categories.

### 2b — Intro / advertising / repeated segments

Debate recordings contain non-debate material: host monologue, sponsor reads, outro calls-to-action, and repeated teaser clips. All of this enters the pipeline unchanged.

**Key constraint from observed data:** The intro is not always at the beginning. Mid-roll ads can appear anywhere. There may or may not be a moderator. This rules out simple timestamp-based or speaker-count heuristics — boundary detection requires semantic understanding of the content.

Example: in the "Debate Alimentario" transcript, turn 10 (start_ms 88,880) contains the formal podcast intro monologue embedded *after* six turns of actual debate content, within the same utterance block as debate content.

## Design Decisions (Resolved)

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Modify stored transcript? | **No** — create a preprocessed version | Original is ground truth; timestamps must stay aligned to audio |
| Claim text rewrite acceptable? | **Yes** | Users accept light rewrites like "Ancel Keys (referido como 'Kiss')" |
| Cleaning trigger | **User-triggered** | Gives control; avoids silent changes |
| Show normalization diff to user? | **Yes** | Users validate before analysis runs |
| Use debate motion to scope normalization? | **Yes, when provided** | The optional motion field already exists; pass it to the entity normalizer as domain context |
| Parallel vs. sequential fact-checking? | **Parallel** (see below) | Speed without quality loss, given correct setup |

---

## Parallel vs. Sequential Fact-Checking

Each `verify_claim()` call is independent (one claim + evidence → one verdict). This is a natural candidate for parallelism.

### Parallel

| Pros | Cons |
|------|------|
| N claims checked in the time of ~1 | Entity glossary **must** be fully built before the loop starts — no lazy resolution |
| Much faster UX for large debates (15 claims: ~15s instead of ~150s) | Burst API usage may hit rate limits on lower Anthropic tiers |
| Evidence fetching (Wikipedia, DDG, Semantic Scholar) is already parallel per-claim | More complex error handling — partial failures need graceful degradation |
| Claims are fully independent, no shared state needed | Progress tracking shows count ("X of N done") but not which specific claim is running |

### Sequential

| Pros | Cons |
|------|------|
| Simpler implementation | Much slower — bad UX for long debates |
| Easy deterministic progress bar | — |
| Could lazily build glossary as entities are encountered | Lazy glossary build defeats the purpose: first claims get no glossary context |

### Verdict: Parallel, with synchronous pre-build

Build the entity glossary synchronously first (one Claude call, ~5–10s), then fan out all `verify_claim()` calls in parallel. This avoids the lazy-build problem entirely while keeping the UX fast. Error handling should allow partial failures: a verdict of `unverifiable` with a logged error is better than blocking the whole batch.

## Solution Architecture

### Pre-analysis cleaning phase (new `transcript_cleaner.py`)

User-triggered, runs once before the first analysis of a given transcript. Output stored alongside the transcript so subsequent re-runs skip this step.

```
Raw Transcript (stored in DB, never modified)
       ↓  [user clicks "Clean transcript"]
  transcript_cleaner.py
    Step A: Boundary detection
      - One Claude call over the full transcript text
      - Identifies debate vs. non-debate segments semantically
      - Uses debate motion (when provided) as domain context
      - Output: list of utterance ranges tagged out_of_scope
      - UI: shows user what will be excluded → user confirms
    Step B: Entity normalization
      - One Claude call over the full transcript text
      - Input: transcript text + debate motion (when provided)
      - Output: entity glossary {surface_form → canonical_name + description}
        e.g. "Kiss" → "Ancel Keys — American nutritionist, creator of the Seven Countries Study"
      - UI: diff view showing all normalizations → user confirms
       ↓
  Preprocessed Analysis Transcript (derived artifact, stored separately)
    - Utterances tagged out_of_scope are filtered by segmenter
    - Entity glossary attached as metadata
       ↓
  [Existing pipeline: segmenter → extractor → classifier → threader → deduplicator]
    - Extractor receives entity glossary: rewrites ambiguous entity references in claim text
      e.g. "Los trabajos de Kiss" → "Los trabajos de Ancel Keys (referido como 'Kiss')"
    - Claim text rewrite is acceptable for display (confirmed)
       ↓
  [Run Fact-Check]
    - Entity glossary built once, passed to every verify_claim() call
    - All verify_claim() calls run in parallel
    - Verifier prompt includes glossary as debate_context block
```

### Fact-check pipeline with entity context

```python
# Before parallel loop — build glossary once
glossary = build_entity_glossary(transcript_text, motion=motion)

# Parallel fan-out
with ThreadPoolExecutor() as pool:
    futures = {
        pool.submit(verify_claim, claim, evidence[claim["id"]], glossary, api_key): claim
        for claim in checkable_claims
    }
```

`verify_claim()` signature addition:
```python
def verify_claim(claim: dict, evidence: list[dict], glossary: dict, api_key: str) -> dict:
```

Verifier user message addition:
```

- Ancel Keys: American nutritionist, creator of the Seven Countries Study.
  Referred to in this debate as "Kiss", "Ansel Kiss", "Ancel Keys".
- Seven Countries Study: Longitudinal cohort study begun 1958…
```

## Recommended Implementation Order

1. **`verifier.py` — add glossary injection** (no new pipeline step, no new API calls)
   Immediate fix for Problem 1. Pass the entity glossary (even manually created for testing) as `debate_context`. Validates the prompt design before building the automated glossary.

2. **`truth_checker/entity_glossary.py` — glossary builder**
   Automates step 1. One Claude call, stored result, injected into verifier and extractor. Fixes Problem 1 fully including edge-case cross-turn references.

3. **`extractor.py` — entity-aware claim text**
   Pass the glossary to the extractor so extracted claim texts use canonical entity names. Fixes Problem 1 at the source for all downstream stages.

4. **Parallelize `verify_claim()` loop in `app.py`**
   Speed improvement. Requires glossary to be built first (already done in step 2). Straightforward `ThreadPoolExecutor` fan-out with partial-failure handling.

5. **`transcript_cleaner.py` — boundary detection**
   Addresses Problem 2b. More complex (semantic, no heuristic shortcut given mid-roll ads and variable structure). Implement after the entity normalization path is validated.

### Prompt 4 — Parallelize the fact-check loop in `app.py`

```

Read truth_checker/evidence.py (the retrieve_evidence function signature).
Read truth_checker/verifier.py (the verify_claim signature after Prompt 1).

       from concurrent.futures import ThreadPoolExecutor, as_completed

2. Before the parallel loop, retrieve the entity glossary from session state:
       glossary = st.session_state.get("entity_glossary", {})

3. Define a worker function inside the fact-check block (not at module level):
       def _check_one(claim):
           evidence = retrieve_evidence(
               claim.get("suggested_query") or claim["text"],
               language=transcript_lang,
           )
           return claim["id"], verify_claim(claim, evidence, glossary, anthropic_key)

4. Replace the sequential loop with:
       verdicts: dict = {}
       prog_fc = st.progress(0, text=LABELS["prog_factcheck"][lang].format(i=0, n=len(checkable)))
       max_workers = min(len(checkable), 10)
       with ThreadPoolExecutor(max_workers=max_workers) as pool:
           futures = {pool.submit(_check_one, claim): claim for claim in checkable}
           for i, future in enumerate(as_completed(futures), 1):
               claim = futures[future]
               try:
                   claim_id, vdict = future.result()
               except Exception as exc:
                   claim_id = claim["id"]
                   vdict = {
                       "claim_id": claim_id, "verdict": "unverifiable",
                       "confidence": 0.0,
                       "explanation": f"Error during fact-check: {exc}",
                       "for_the_claim": "", "against_the_claim": "",
                       "key_source": "", "all_sources": [],
                   }
               verdicts[claim_id] = vdict
               prog_fc.progress(
                   int(i / max(len(checkable), 1) * 100),
                   text=LABELS["prog_factcheck"][lang].format(i=i, n=len(checkable)),
               )

5. Keep the lines after the loop unchanged:
       st.session_state["verdicts"] = verdicts
       st.rerun()

Do not change the checkable-claims filter, the progress bar label strings,
the session state key "verdicts", or any code outside the fact-check block.
```
